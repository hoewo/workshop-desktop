# Workshop 记录技能拆解草案

Status: draft

Date: 2026-06-23

Source: [workshop-product-concept.md](workshop-product-concept.md)

## 当前判断

Workshop 这一阶段先围绕“记录”拆能力，不按项目规划、任务系统或知识库来拆。

它要解决的是：人在和 AI 深度推进项目时，重要想法、判断、取舍、执行结论和后续提醒能被快速记下、看懂、整理，并在之后继续被 Codex 使用。

## 拆解原则

- 记录先给人看，不先给系统分类。
- 正文是主要内容，标注只是辅助检索。
- 默认记录短、清楚、能回看。
- AI 可以帮助写、整理、生成页面，但不能把记录变成复杂表单。
- Codex 可以生成新记录；改写已有记录需要用户确认。
- HTML 页面是帮助人理解和整理记录的表达方式，不是新任务系统。

## 记录技能 1：快速写下

用户动作：

- 打开记录入口。
- 直接写，不需要先选类型。
- 写完自动保存。
- 后续再决定是否关联项目、发送 Codex 或整理。

产品要求：

- 入口接近记事本。
- 正文编辑是主体验。
- 分类、状态、转任务、归档等动作不能抢主视觉。
- 空白状态只鼓励开始写，不解释复杂功能。

需要拆解：

- 当前记录窗口里哪些按钮会干扰写作。
- 新建记录时默认展示什么。
- 项目归属、发送 Codex、转任务这些动作放在什么层级。

## 记录技能 2：把内容写清楚

记录不是流水账，也不是正式 PRD。默认写成后续能读懂的短内容。

基础结构：

- 结论：这条记录最重要的判断是什么。
- 依据：为什么会有这个判断。
- 影响：它会影响后续什么。
- 下一步：后面要做、验证或注意什么。

不同内容的关注点：

- 灵感：想到什么，为什么可能有价值，什么时候再看。
- 产品判断：选择了什么，放弃了什么，影响什么体验。
- 架构取舍：为什么这样做，约束是什么，后续风险是什么。
- 执行结论：这次做了什么，结果如何，下一步是什么。
- 未来规划：想推进什么，前置条件是什么，暂时不做什么。
- 风险问题：问题是什么，可能影响什么，怎么验证。

需要拆解：

- 形成 5-6 个短记录模板。
- 每个模板都控制在几行内。
- 不做强制类型，只作为 AI 和用户写记录时的参考。

## 记录技能 3：AI 被动写入

AI 写入记录的典型时机：

- Codex 完成一次任务后。
- 讨论形成稳定结论后。
- 用户明确要求“记录一下”。
- AI 发现当前结论会影响后续开发。

默认写什么：

- 结论。
- 影响。
- 下一步。

默认不写什么：

- 完整对话。
- 完整推理过程。
- 测试长日志。
- 大段代码细节。
- 没确认的长期事实。

需要拆解：

- Codex 完成后默认生成什么格式的短记录。
- 什么情况下新增记录，什么情况下建议追加到已有记录。
- AI 写入时标题如何生成。

## 记录技能 4：AI 生成 HTML 整理页

HTML 页面不是为了“好看”，而是为了让人更容易理解和整理记录。

适合的页面：

- 多条记录归纳。
- 方案对比。
- 决策过程梳理。
- 下一步建议。
- 新记录候选列表。
- 写入前确认页面。

当前阶段的定位：

- 先作为临时整理页或确认页。
- 页面可以丰富、有结构、有视觉层级。
- 页面不能直接获得 Workshop 写权限。
- 用户确认后，Workshop 执行新增记录、追加正文或标注等动作。

需要拆解：

- 做 2-3 个 HTML 页面样例。
- 每个样例说明它帮助用户理解什么。
- 验证它是否比纯 Markdown 更适合整理和判断。

## 记录技能 5：和 Codex 双向使用

用户到 Codex：

- 用户把一条记录发送给 Codex。
- Codex 使用记录正文理解背景和目标。
- 发送动作由 Workshop 服务层完成。

Codex 到 Workshop：

- Codex 默认只能新增短记录。
- 如果要追加或改写已有记录，必须走确认页。
- Codex 不能绕过 Workshop 直接改内部文件。

需要拆解：

- 发送给 Codex 的记录内容怎么组织。
- Codex 完成后短记录怎么写。
- 追加已有记录的确认页怎么展示变更。
- 失败、限流、中断时给用户看什么。

## 记录技能 6：轻量标注

标注用于检索和整理，不替代正文。

可以有：

- `intent`：这条记录大概是什么意图。
- `retention`：临时、保留、候选、归档。
- `resolution`：开放、已回答、已决定、已转化、已过期。
- `tags`：少量关键词。
- `relatedRecordIds`：相关记录。
- `relatedTaskId`：相关任务。

不应该有：

- 长摘要。
- 正文替代品。
- 强类型系统。
- 大量用户必须填写的字段。

需要拆解：

- 哪些标注字段第一阶段真正需要。
- 标注是否先只给 AI 用，不急着做复杂 UI。
- 标注如何从记录正文中重新生成。

## 当前不做

- 不做完整任务系统。
- 不做复杂项目管理流程。
- 不做完整知识库。
- 不强化后端同步。
- 不把登录账号作为主线。
- 不要求用户填写复杂表单。
- 不把记录变成任务、决策、迭代或 repo fact 的类型系统。

## 下一步先拆三件事

### 1. 记录入口减法

看现有记录窗口，把会干扰“快速写下”的动作分成三类：

- 保留在主界面。
- 放进次级入口。
- 当前阶段隐藏或弱化。

### 2. 记录模板

先写出几类最常见记录的短模板：

- 灵感。
- 产品判断。
- 架构取舍。
- 执行结论。
- 未来规划。
- 风险问题。

### 3. HTML 整理页样例

先做少量样例验证表达方式：

- 一页记录归纳。
- 一页方案对比。
- 一页写入确认。

这三件事完成后，再决定是否进入界面改造和 Codex 回写实现。
