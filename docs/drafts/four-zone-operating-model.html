总览 事实源 晋升流 项目类型 规则
不是一个工具包办全部，而是一套跨工作区协议

最小闭环是个人区和代码区，其他区按需启用。

四区模型把研发活动拆成个人区、产品工作区、项目管理区和代码工作区。默认先跑通个人思考到代码事实的闭环；当出现协作、承诺、交付或长期产品判断时，再打开产品工作区和项目管理区。

个人区负责捕捉和判断，不直接变成需求、任务或 repo fact。
代码工作区负责实现、测试和发布，让事实从运行结果中回流。
产品工作区和项目管理区是外部协作层，只有需要产品沉淀或执行承诺时才启用。

每个区都有自己的实现方式和事实源。

通用方案不替代专业工具，只避免事实源混乱。一个项目可以接入外部工具，也可以保持极简。

个人区保存原始思考

owner: individual
  • 可以不完整、不正式、不协作。
  • 记录触发点、判断、下一步。
  • 作为需求、任务、决策的候选材料。

产品区保存产品判断

owner: product workspace
  • 用户问题、市场假设、PRD、交互稿。
  • 面向协作和复用，而不是个人流水账。
  • 可以由外部文档或设计平台承载。

管理区保存执行承诺

owner: project system
  • 目标、迭代、任务、里程碑、验收。
  • 外包项目尤其需要清晰变更和责任边界。
  • 不应该替代产品论证或技术事实。

代码区保存长期工程事实

owner: repository
  • 源码、测试、发布流程、架构边界。
  • 只写稳态事实，不写个人脑暴和临时任务证据。
  • 事实冲突时先核实现有运行行为。

真正通用的是晋升流水线。

四区之间不复制全文，只传递被确认的结果、引用和元信息。这样项目可以轻，也可以重。

01

个人捕捉

写下想法、问题、风险、直觉和下一步。允许短、散、未定。

02

AI 整理

提取候选需求、任务、决策、知识点。保留来源，不伪装成事实。

03

人工确认

用户判断是否值得协作、承诺、长期维护，决定进入哪个区。

04

外部工作区承接

产品文档、项目任务、客户交付规范或 repo 文档分别接住自己的内容。

05

生产事实回流

代码、测试、发布和验收结果形成稳定事实，再作为后续判断的证据。

闭环不是一条线，而是三种回流。

线性晋升解决“往前推进”，回流关系解决“做完以后如何修正下一轮判断”。这也是四区模型比单一文档或单一看板更稳的地方。

  • 个人反馈回流：使用、沟通和执行中的新判断回到个人区。
  • 产品决策回流：评审结果修正需求、交互和范围。
  • 代码事实回流：实现约束、测试和发布结果反过来约束产品与任务。

不同项目，是在最小闭环上打开不同外层。

默认启用个人区和代码区。点击左侧项目类型，查看产品工作区和项目管理区在什么条件下被打开，以及各自的闭环如何回流。

前期探索主要依赖个人区，MVP 连接代码工作区；只有进入正式立项或生产级，才逐步打开产品区和项目管理区。

最小闭环

个人区和代码区先跑通，再按协作需要打开外层。

    让方案通用，需要守住三条规则。

    规则越清楚，工具越可以自由替换；规则不清楚，任何工具都会变成混合垃圾桶。

    RULE 01

    事实源不能互相冒充

    个人记录不是任务，任务不是产品判断，产品文档不是运行时事实，repo 文档不是会议纪要。

    RULE 02

    跨区只传晋升结果

    跨区流转时传递结论、证据、引用和状态，不把全文复制到每个地方。

    RULE 03

    协作强度决定流程强度

    不协作时个人区到代码区即可；协作、外包、生产级项目才启用更强产品和项目治理。

    Workshop Desktop 的稳态位置：个人区与执行桥。

    它不需要实现完整产品工作区或项目管理区。更好的方向是管理当前注意力、记录个人材料、连接本地项目目录、把成熟内容送往外部工作区或代码执行。

    承载个人记录、本地项目、当前上下文、Codex 执行入口
    连接产品文档、任务系统、repo、客户规范
    不包办完整知识库、完整项目管理系统、全部产品文档平台
