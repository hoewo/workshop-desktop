# Workshop Desktop · 形态决断决策文档

Status: draft

Date: 2026-06-25

Source: [讨论纪要](workshop-direction-discussion.md) + [方向对比报告](workshop-direction-comparison.md) 收束后的核心决断。本文专门为"产品形态选择"做独立、可独立理解决策的说明。

> 三场圆桌 + 八轮探讨收敛到一个比"选哪个方向"更本质的决断：**产品形态保持 Electron 桌面端，还是转为 hooks/plugin 编排层？** 这个决断决定 D8-b（团队记忆）生死，也决定 D5（个人多厂商聚合）是否为唯一活路。
> 本文对两种形态做充分说明，并用选项卡把二选一呈现给产品决策者。

---

## 0. 为什么要做形态决断

前几轮把"方向"穷尽了——内容主轴（任务/记录/连续性/碎片）全部判死，权限/审计维度（D7）被代码层证伪（架构死锁）。唯一没被判死的是两个"跨厂商聚合"方向：

- **D5**（个人尺度多厂商聚合）：唯一未占空位，但需求未验证。
- **D8-b**（团队记忆，hooks/plugin 形态）：物理前提已坐实（Codex+Claude 两侧 hook 门都开）、独占增量真实（跨人流转）、激励自反不成立。

关键洞察：**D8-b 的成立不取决于"方向对不对"，取决于"形态愿不愿转"**——因为它需要的 hooks/plugin 物理形态，与当前 Electron 桌面端是两套不同的东西。这不是功能扩展，是产品形态重定义。两个端点之间**没有连续路径**（马斯克判据）。

所以决断从"选哪个方向"下沉到"选哪个形态"。

## 1. 两种形态的本质差异

### 形态 A：Electron 桌面端（当前形态）

**是什么**：一个常驻操作系统的 GUI 应用。主进程拥有窗口、托盘、快捷键、本地文件、app server、Codex 派发能力。

**物理形态特征**：
- 有 UI（窗口、托盘面板、便签、设置页、确认页、任务预览、更新窗口）。
- 用户主动打开使用，是"工作台"——人坐在它面前做事。
- 本地状态归属：本地 markdown 记录、配置、运行状态表都在它自己的 userData 目录。
- 通过 app server(127.0.0.1) + 受限 token 对外提供能力。

**当前代码已落地的独有能力**（核实于 `src/main/main.ts`）：
- `Tray` 托盘常驻、`BrowserWindow` 多窗口（主页/托盘/便签/记录/设置/手册/更新/任务预览）
- `globalShortcut` 全局快捷键
- `ipcMain` 主进程-渲染进程桥接、`dialog` 系统对话框
- app server + 受限 token + 确认页 + origin 标记 + 运行状态表 + Codex 派发

> 这些 UI 与入口能力是 hooks/plugin 形态**给不了**的——hooks 是无 UI 的事件处理器。

### 形态 B：hooks/plugin 编排层（目标形态）

**是什么**：不是一个独立应用，而是一组挂在 Codex/Claude hooks 上的事件处理器 + 一套跨厂商的"人对 Agent 说 no"的规则格式。物理下限是**一个 plugin/hooks 目录 + 几个读 stdin 写 JSON 的脚本，几十到几百行**。

**物理形态特征**：
- **无独立 UI**——它寄生在 Codex/Claude 自己的进程里，靠 Agent 的 hook 事件触发。
- 不是"人坐它面前做事"，是"Agent 执行时它被动介入"。
- 不持有本地状态（或只持有规则配置），状态散在 Agent 自己的 session/vault 里。
- 物理可达性已坐实（核实于 Codex `codex-rs/`）：
  - `hook_runtime.rs:56` `PreToolUseHookResult::{ Continue{updated_input}, Blocked(String) }`
  - `registry.rs:505` `Blocked => return Err(FunctionCallError)`，阻断工具执行
  - 事件枚举：PreToolUse / PostToolUse / PermissionRequest / SessionStart / UserPromptSubmit / SubagentStart / SubagentStop / Stop / PreCompact / PostCompact
  - Claude Code 侧同样有 PreToolUse + `permissionDecision:"deny"`

**部署门槛**（核实于 `codex-rs/config/`、`core/src/config/mod.rs`）：
- Codex hooks 默认需 `persisted hook trust`（`trusted_hash`），不信任的 hook 不运行。
- 可用 `--dangerously-bypass-hook-trust` 绕过但启动时告警。
- 即第三方 hooks 有"用户主动信任"的部署摩擦，不是零成本即装即用。

## 2. 两种形态对产品能力的影响（逐项对比）

| 维度 | 形态 A：Electron 桌面端 | 形态 B：hooks/plugin 编排层 |
|---|---|---|
| **UI/入口** | ✅ 托盘/窗口/快捷键/便签/确认页全套 | ❌ 无独立 UI，寄生 Agent 进程 |
| **能否"人对 Agent 说 no"拦截执行** | ❌ 架构死锁（D-008 给 Codex 注入 agentToken，scope guard 拦在 confirmation.request 之外；AGENTS.md:54 要求 agent 按门铃但代码让 agent 没手）| ✅ PreToolUse+Blocked 直接阻断工具执行，两厂商都开 |
| **本地状态归属** | ✅ 自有 userData（记录/配置/运行表） | ⚠️ 无自有状态，散在 Agent session/vault |
| **跨厂商编排** | ❌ 只能派发 Codex，不通 Claude | ✅ 可同时挂 Codex+Claude，定义统一"no"规则 |
| **团队多成员协作** | ❌ 单机本地 markdown，无多用户/同步/权限 | ⚠️ 形态本身不解决，但比 Electron 更可能挂共享规则 |
| **部署摩擦** | ✅ 装一个 app 即用 | ⚠️ 需用户主动信任 hook（trusted_hash），有门槛 |
| **可被既有方案覆盖** | 高（Obsidian/平台 session/后端压扁各方向）| 低（激励自反不成立，平台结构性不做） |
| **当前代码可复用度** | —（就是当前形态） | 仅 app server+token+scope 模板可迁移，UI/确认页沉没 |

## 3. 两种形态各自能兑现哪些方向

| 方向 | 形态 A（Electron） | 形态 B（hooks/plugin） |
|---|---|---|
| D1 任务入口 | 寄生后端，判死 | 不适用 |
| D2 极简记录 | Obsidian 占满，判死 | 不适用 |
| D3 单厂商连续性 | 平台 session 占满，判死 | 不适用 |
| D4 碎片收容 | Obsidian+MCP 覆盖，判死 | 不适用 |
| D5 个人多厂商聚合 | ✅ 唯一未判死活路（需重做数据模型+验证） | 可承载，但个人尺度不如团队有刚需 |
| D6 插件化归宿 | 不是 Electron | ✅ 本身就是插件形态 |
| D7 权限网关 | 架构死锁判死 | ✅ PreToolUse+Blocked 就是"人对 Agent 说 no" |
| **D8-b 团队记忆** | ❌ 判死（单机做不了团队） | ✅ 三前提全满足（物理可达+跨人流转+激励自反不成立） |

**核心洞察**：形态 A 只能兑现 D5（且需验证）；形态 B 能兑现 D5+D6+D7+D8-b 四个方向的合流。**形态 B 是前几轮所有判活碎片的共同归宿，形态 A 只守得住 D5 一个孤岛。**

## 4. 两种形态的产品影响（充分说明）

### 形态 A 的影响：保持现状

**对产品身份的影响**：仍是"个人当前注意力工作台"（D-003/D-014 已接受定位）。产品边界不变，仍是个人工具。

**对能力的影响**：保留全部 UI 与入口（托盘/窗口/快捷键/便签/确认页），这些是已落地资产。但 D7 已证这些 UI 上的"确认页"在权限/审计维度是死锁的——agent 按不了门铃。所以确认页只能继续做"Workshop 自身数据 CRUD 的确认"，做不了"对 Agent 说 no 的治理"。

**对路径的影响**：唯一能走的是 D5（个人多厂商聚合）。需重做 recordStore 数据模型（存推理链快照+来源厂商），且**需求未验证**——曼昆的聪明做法是把可迁移资产（app server+token+scope 模板）投到 D5 跑两周真实使用，零使用则 D5 也是尸体。

**致命风险**：D5 若验证失败，形态 A 就没有未判死的方向了——产品承认无独立位置，转 D6（把思想做成 Obsidian/IDE 插件，放弃 Electron）。即**形态 A 是"赌 D5 一个孤岛"，输了就退守插件化。**

**保留价值**：托盘常驻 + 全局快捷键 + 便签这套"系统级入口 + 轻量工作面"是形态 A 独有的，若个人开发者真有"随手记/随手派发"的高频需求，这套 UI 有价值——但前提仍是"有人用"，而当前是零使用。

### 形态 B 的影响：转为 hooks/plugin 编排层

**对产品身份的影响**：从"独立桌面应用"变为"跨厂商 Agent 协作的治理/记忆编排层"。**失去独立产品身份**——它不再是一个用户打开的 app，而是一组 Agent 执行时被动介入的规则与处理器。这可能是 Workshop 思想（受控回写/确认/origin 来源）的正确归宿，也可能意味着"Workshop 作为一个产品名消失了，思想活在 hooks 里"。

**对能力的影响**：
- 失去：全部 UI、托盘、快捷键、便签、自有本地状态。
- 获得：真正能"人对 Agent 说 no"拦截执行（PreToolUse+Blocked），跨厂商统一规则（Codex+Claude 同一套"no"账本），这是前几轮判活的 D5+D7 在新形态下兑现。
- 部署从"装 app"变为"配置 hooks + 信任"——有 trusted_hash 摩擦，但比多厂商聚合需重做数据模型轻得多（几十到几百行 vs 推倒重做）。

**对路径的影响**：D8-b（团队记忆）成为主方向。但 D8-b 仍需验证两件事：①团队记忆"跨人流转+中立性"真实需求（需 dogfood，依赖至少两人协作场景）；②Codex hooks 的信任模型在实际部署中会不会卡住（`--dangerously-bypass-hook-trust` 是逃生口但会告警）。

**致命风险**：
- **形态断裂不可逆**——从 Electron 到 hooks/plugin 没有连续路径，转了就回不去（UI/托盘/便签全部沉没）。
- **D8-b 需求未验证**——物理前提成立≠需求成立。团队记忆需要"多人+多厂商协作"的真实场景，而当前连个人单厂商都没人用。
- **失去独立可见性**——hooks 产品难有独立品牌/分发，可能被吸收进 Codex/Claude 生态。

**潜在收益**：若 D8-b 需求成立，这是前几轮唯一同时满足"物理可达+独占增量真实+激励自反不成立"的方向，且是 D5×D6×D7 的合流归宿。

## 5. 决策的真正分叉

这个决断的本质不是"哪个形态更好"，是**产品决策者要回答的一个问题**：

> **你要的 Workshop，是一个用户打开的桌面工作台，还是一组 Agent 执行时被动介入的治理规则？**

- 前者 → 形态 A，赌 D5 个人多厂商聚合一个孤岛，输了退守插件化。
- 后者 → 形态 B，押 D8-b 团队记忆合流归宿，但需验证需求且形态不可逆。

**两个形态不能同时做、不能渐进迁移**——这是马斯克"两个端点之间没有连续路径"判据的核心。资源有限，必须二选一，或承认现在不决断（=默认留在形态 A，继续零使用）。

## 6. 我的倾向（仅供参考，决策权在产品决策者）

如果非要给倾向：**形态 B 的天花板更高、前提更硬，但不可逆且需求未验证；形态 A 是已知会输的赌注（D5 验证失败概率高）但可逆。**

- 若你**确信有多人协作场景**且愿意接受形态断裂 → 形态 B（D8-b）。
- 若你**不确定团队需求、想先验证个人多厂商聚合**且不愿现在断 UI → 形态 A（D5 两周验证），输了再转 B。
- 若你**两者都不确定** → 默认形态 A + 跑 D5 dogfood，用数据替代猜测，而非再讨论。

但必须提醒（荣格诊断）：**"两个都不确定所以先不做决断"就是判据延迟。** 留在形态 A 零使用，本身就是一种决断——决断"不转形态"，而它的结果已经在运行时数据里写死了：零使用。

## 附：决断后的下一步（无论选哪个，都不是再开圆桌）

- 选形态 A → 跑 D5 两周 dogfood（把 app server+token+scope 模板投到多厂商聚合），用运行数据判 D5 死活。
- 选形态 B → 先做 D8-b 最小验证：一个 PreToolUse hook 脚本 + 一次真实跨厂商协作，看"跨人流转 + 人对 Agent 说 no"是否被需要。
- 选不决断 → 默认形态 A + 零使用持续，等于决断"产品停滞"。
